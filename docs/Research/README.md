# Research

Notes that capture investigations into how the field handles a problem before we make a load-bearing decision. The audience is future-us — we keep these so the reasoning behind a non-obvious choice doesn't have to be re-derived from chat scrollback.

Commit SHAs, PR and issue numbers, and branch names in these notes refer to the project's pre-publication history and are not present in this repository's history.

## When to add an entry

- A frontier-search session produced findings worth keeping (sources, version notes, GitHub maintenance signals).
- A judgement call on a plan or design referenced external practice; record what we found and what we picked.
- A deep-dive into a paper or codebase informed an Aski-specific decision.

Skip when: the question was a one-off lookup with no downstream impact, or the findings already live in a spec/plan unchanged.

## Discoveries log

Deep-dive investigations get their own dated file under this directory (see "When to add an entry" above). Quick-capture cross-cutting insights — a connection between research areas, a technique from one pipeline stage that might help another, a surprising finding worth retesting — go into [Discoveries.md](Discoveries.md) as a single appended entry, not a new file.

Add a discovery entry when, mid-task, you notice something worth revisiting that's out of scope for what you're currently working on. The Discoveries.md header explains the entry format and triage workflow.

## Filename convention

`YYYY-MM-DD-<slug>.md`.

## Lifecycle

Top-level entries are limited to research notes, `README.md`, `Discoveries.md`,
`index.json`, and `Corpus/`. Put reusable datasets under `Corpus/` with a
`manifest.yaml`. Do not commit ad hoc screenshots, CSVs, HTML reports, or
scripts directly in `docs/Research/`.

Use `active` only when the note has an open `next_action` or is still driving a
current decision. Use `complete` once the decision and evidence are recorded.
Use `superseded` when a newer note replaces the conclusion, and `archived` when
the note remains historical context only. Living notes are rare and should be maintained deliberately; they use an undated
filename stem (e.g. `TileGridInternalHardening.md`) — the date/filename-prefix parity
check only applies to ISO-dated stems, by design.

Execution placeholders such as `<date-executed>`, `<RUN_DATE>`, and unresolved
SHA placeholders are not allowed in committed research notes or manifests. If a
plan uses placeholders, resolve them before committing the resulting artifact.

A brief or rule note that asserts an `@_spi(AskiResearch)` entry point exists must cite it as
`file:line` against the current checkout and name its access level; the standing research
rules live in [../agents/research-methodology.md](../agents/research-methodology.md).

## Structure

Each entry should answer:

1. **Question** — what triggered the research, in one paragraph.
2. **What the field says** — primary sources, dated; quote concretely when the wording matters; flag GitHub maintenance signals (active vs archived) when a tool is referenced.
3. **What we picked, and why** — the Aski-side decision, with the trade-off and any out-of-scope follow-ups.
4. **Sources** — markdown links, grouped if there are many.

Keep entries tight. If a finding belongs in a spec, link to the spec and only summarize here.

## Front-matter

Every note carries YAML front-matter — the source of truth for the generated index below and for `index.json`. Required fields: `title`, `slug` (the filename stem), `date` (`YYYY-MM-DD`; for dated filenames it must match the prefix), `status`, `subsystem`, and `summary`. Optional fields, omitted when empty: `related_specs`, `next_action`, `datasets`, `runners`.

- **`status`** — one of `living` (continuously updated), `active` (open threads or a pending `next_action`), `complete` (decision recorded), `superseded`, or `archived`.
- **`subsystem`** — a list drawn from `color-science`, `shape-context`, `tile-grid`, `animation`, `frontier`, `meta`.
- **`summary`** — one double-quoted paragraph of plain prose. No inline markdown links; put spec and plan links in `related_specs` instead. This is what the generated index renders.
- **`related_specs`** — repo-relative paths, validated to exist on disk by `ResearchRegistryTests`.
- **`datasets`** — repo-relative corpus paths under `docs/Research/Corpus/`, each with a validated `manifest.yaml`.
- **`runners`** — names of `Tools/` executables that reproduce the work (e.g. `AskiColorLab`).

Use double-quoted scalars for text fields and inline lists (`[a, b]`) for list fields; the parser is intentionally minimal and rejects anything outside that subset. Run `swift run BuildResearchIndex` after editing front-matter to refresh the index.

- [2026-08-19 — Sampling-Lattice Support Collapse - the shipping 60D descriptor carries 2-3 bins](2026-08-19-sampling-lattice-support-collapse.md) — Structural result, decisive by arithmetic and confirmed empirically. The converter caps its thumbnail's longest side at columns times oversample, so at the default oversample of 2 the per-cell source patch is exactly 2 pixels wide on every image, at every column count. ShapeContext.histogram60 then admits a pixel only when its radius falls in the half-open band between 0.5 and min(width,height)/2, which for a 2-pixel-wide cell admits 2 or 3 pixels out of 8 and reaches 2 or 3 of the 60 bins - one bin per admitted pixel. After L1 normalization the shipped 60-dimensional log-polar shape context is a one-to-two parameter vertical-asymmetry statistic. A sweep of source aspect from 3 to 1 through 1 to 3, read back from the converter's own resolved geometry, shows every aspect landing on the same 2 by 4 footprint at columns 80, so the collapse is not an artifact of one image shape. Cell-height parity flips which bins are reachable - even heights land in radial bin 4, odd heights in radial bin 0. The current exact-lattice 3072-square census finds transitions through column 16 and none above 16, so the discontinuity is real in the thumbnail regime and never fires at the frozen preset's 76 columns.
